# 技术决策记录

日期：2026-10-29。以下为开发方案，可随证据调整；业务边界按固定理论编号维护。

| 决策 | 当前选择 | 原因 | 何时重评 |
| --- | --- | --- | --- |
| ADR-001 应用结构 | 模块化单体，前端/API/worker共享业务契约 | 减少重复数据和跨服务状态不一致，保留替换边界 | 独立扩展、安全隔离或实际负载证明需要拆分 |
| ADR-002 数据核心 | PostgreSQL、不可变来源版本、明确分项行动 | 事实、问题、覆盖和报告状态不同，不能只保存聊天文本 | 新部署环境或验证发现模型不够用 |
| ADR-003 人工与AI | 明确计算由程序执行，AI提取/分析/草稿，用户按职责确认 | 可解释、可复核且符合用户实际工作 | 具体用途验证后才提升自动程度 |
| ADR-004 自动范围 | 只自动核对检验报告；V1A允许人工确认源字段，V1B接OCR | 保留核心工作流并满足用户允许分期的要求 | 用户明确提出新的自动范围 |
| ADR-005 业务配置 | 规则、模板、目录作为版本化数据，不写死协议数字 | 新项目和规则更新通常无需改底层代码 | 出现无法表达的条件再扩展规则契约 |
| ADR-006 资料检索 | 首先结构与关键词检索，不先部署向量平台 | 当前更需要原文、条件和适用性完整 | 中文召回等测评显示需要补充 |
| ADR-007 理论同步 | 固定编号、模块对应、内容指纹、变更记录及CI | 能定位漏同步，不保证语义判断自动正确 | 出现映射范围或维护成本不足 |
| ADR-008 GitHub云 | 公开仓库仅放代码/设计/合成样例；Codespaces开发，Actions验证 | 用户要求云上开发，临床资料有实际保密边界 | 用户选定获准私有试用环境 |
| ADR-009 任务队列 | PostgreSQL job表和worker，先不增加Redis/Celery | 运行组件更少，作业仍可持久追踪 | 负载、吞吐或延迟数据证明需要 |
| ADR-010 依赖策略 | 采用成熟库，W01/W02核实并锁定精确版本 | 不从头写OCR、数据库驱动和表格解析；不把技术建议写成已验证实现 | 安全更新、许可证或兼容性变化 |

不采用隐藏供应商依赖、不把四业务模块做成四份独立问题库、不把任何新上传文件自动覆盖旧规则、不把所有遗留完成口径统一为一张复杂证明表。
