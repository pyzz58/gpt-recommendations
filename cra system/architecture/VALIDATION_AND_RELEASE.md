# 开发完成、能力验证和发布

技术设计v0.4；对应M13/M14及各业务模块验收。工程检查用于证明代码和执行记录，临床用途按具体范围另外验证。任何环节都不增加CRA确认整改、PD已上报或普通交接的额外审批。

## 1. 四个完成层次

| 层次 | 证明什么 | 不足以证明什么 |
| --- | --- | --- |
| code_complete | 实际代码/迁移/接口、任务专属集成和构建通过 | 不能只凭mock或空文件；也不证明全部临床用途 |
| synthetic_validated | 明确合成输入、正确预期及完整路径通过 | 不证明未覆盖版式和真实数据分布 |
| provider_validated | 实际配置的OCR/提取/分析provider在独立样例上达到该用途要求 | 不自动获得真实资料处理授权，也不自动等同整体安全 |
| authorized_trial_ready | 实际环境、资料/服务范围、恢复与用途证据具备，可以开展限定试用 | 不宣称全项目/全格式通用认证 |

tasks.json的verified表示该工作包约定工程交付通过，不等于全系统试用就绪。W08的主线含实际识别比较、W04含实际规则提取、W09含实际分析评估，对应任务不能仅靠DisabledProvider完成。W13可以如实汇总未达标结论，但不能把缺核心自动能力的版本命名为完整首版。W15部署与真实操作分开，不在公开CI放真实临床资料。

## 2. 当前已实现的任务完成门槛

tools/task_evidence.py及专属Actions为W01以后完成声明增加以下校验：

1. completion_evidence必须是结构对象，包含kind=github_actions、profile_id、run_id、精确tested_commit和subject_digest；自报文字仍可附说明，但不能单独完成任务。
2. subject_digest绑定实际非空交付文件、profile所列模块/依赖和样本文件、任务条件/步骤/验收、有关理论与CI profile。修改实现或规范后，旧证据失效。
3. 直接查询GitHub运行元数据，核对同仓库、固定CRA工作流、push事件、精确提交和成功结果；按profile核对任务专属job及必需步骤，不接受只有baseline的运行。
4. 完整历史中核对测试提交是当前祖先，测试时文件/规范/profile与现在一致。仅状态、证据和命令availability更新不改变主体指纹，解决“测试通过后再记完成”的循环问题。
5. 证据服务不可用、运行被删除或指定步骤跳过时拒绝放行，重新取得可验证运行；不降级到相信手写声明。W00是有既往证据的历史bootstrap特例，不能挪用为其他业务任务。
6. CI profile是对实际工作流job/步骤的要求，不是可以任意执行的任务JSON脚本。命令应按任务卡在受审查的CI代码中实现，不能eval用户材料或从JSON拼接shell执行。

该门槛证明来源和实际CI运行，不证明测试本身无遗漏；有意义的反例及语义审查仍必要。仓库拥有者有能力改写测试/工作流，不能把同仓库自证包装成独立临床认证。W01首个真实任务通过前，AUD-001的正向真实交付证据仍待补。

## 3. 一项任务如何实际交付

先运行next_task读取当前未完成项→核实前置→读取任务卡的设计输入/进入条件→代码和迁移→实际CI job/profile。实现源码提交C1，在push运行R中完成本任务必需测试；获取R与C1及subject_digest，保存结构证据、更新状态/availability并生成视图，形成状态提交C2。C2不得顺便修改C1已验证的实现、依赖、样本或验收规范；否则重新测试新主体。后续模块修改使已验证任务绑定的源码变化时，只对受影响任务重跑相应CI并更新证据，不重做业务记录。进入源码提交C1前，将这些任务及不能保持有效声明的已验证依赖链标为in_progress，并把旧证据留在completion_history，不能一边改源码一边继续声称旧版本已验证。C1由实际测试生成新证据，C2再恢复verified；这样不会出现旧证据门槛阻止新测试运行的循环。此过程由Codex管理，不增加CRA操作。

基础同步和单元测试一直执行；后续业务专属job在相应任务中真正实现，尚未实现的命令和job不能写成已运行。profile列出的required_steps是稳定契约，增加或调整时同步task、实现、证据和文档。CI不要把所有未实现任务命令立即执行到失败，也不能用跳过测试假装任务成功。

任务结束记录实际文件、命令/运行链接、合成操作结果、限制及下一项；只有达到对应验收才verified。能力未配置可保留代码已实现状态说明，不伪造provider验证，不跳过实质前置。

## 4. 样本和预期设计

tests/fixtures/manifest.json登记artifact_id、格式、用途、development/evaluation组、纯合成/获授权来源、输入哈希、预期定位、标注依据、标注复核和支持范围。开发分组用于修改代码/提示词，独立分组用于固定评估，不能把正确预期送入模型后再声称独立识别成功。

| 样本族 | 必须覆盖 |
| --- | --- |
| RULE | 前提/且或/否定/例外/脚注、C→B/D→F、未知及分析型规则、启用日与中心范围 |
| LAB | 文字PDF/扫描/照片、中文表格、同日初检复查、修订、跨页/两日期、单位/比较符/小数点、歧义与无法识别 |
| CONTEXT | 不同患者标识、date-only/缺锚点、来源冲突、拒绝/恢复与局部继续 |
| CARRYOVER | 旧报告/track/文字、缺字段、复导、选信、直接确认与部分待办 |
| OUTPUT | 模板重复区、未知与覆盖措辞、用户确认来源、历史快照、多份输出一致 |
| SYSTEM | 越权、并发修订、幂等/中断/重试、输入更新后旧job结果、恢复和provider不可用 |

40个固定CRA-S场景沿用，不因为增加样本另起第二份业务清单。场景planned不能通过新增表格变为verified；每项必须有输入/正确预期/实际结果及证据。

## 5. 评判和工作量

按用途分别记录身份/日期误配、条件遗漏、字段错读、单位换算、误报、漏检、错误关闭和超范围结论，不能用一个平均准确率掩盖关键错误。支持范围评估中出现未解决的关键错配、无依据确定性安全结论、假已上报或越权应阻止该用途就绪声明；必要修复后重测。有限样本零观察错误也不等于真实世界零风险。

同时记录文件和字段数、自动可用比例、人工更正/补录比例、集中复核时间、核对/报告/返工及总时间；与同一任务原流程比较。实际阈值由用途风险和代表性样本确定后固定，不能先编一个百分比宣称达标。手工比例或确认负担导致总时间不减，核心减负目标就仍未达到。

W03开始样本和环境探测，W04/W08/W09开始实际provider评估，W06/W08提供早期可观察结果，W11—W12串联完整交付，W13汇总。不能到W13才第一次发现资料格式或识别环境不可用。

## 6. 试用、维护和恢复

W15在获准的私有运行环境核对OIDC身份、TLS、数据库/文件隔离、最小权限、模型数据处理、备份恢复及资料保留策略。公开仓库/CI只含代码、纯合成数据和去敏证据摘要；真实样本/原图/日志与医学资料保留在获准环境，不能为追求CI证据上传公开附件。

UseCase记录用途/用户/输入/输出/可能错误与后果，Validation记录版本和样本结果，Release记录能力与范围，Monitoring记录反馈/漂移/事故/暂停/恢复。具体审阅责任随获准用途明确，放在开发发布层，不给每次监查加审批。模型、OCR、映射、规则结构或依赖升级后，回归受影响用途；发现退化暂停相关自动能力，保留原文件、事实、list和问题工作，验证修复后恢复。

迁移采用兼容增加→核实回填→切换读写→回退演练。实际恢复同时核对文件引用、问题编号、规则版本、审计及签发快照，不只检查数据库能启动。正常备份不等于已经实测恢复。
