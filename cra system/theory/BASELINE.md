# 第一版业务理论基线

基线 CRA-V1-20261029，来自Notion v0.14及用户本轮进入技术设计的指示。这里整理已确认工作方式；完整可定位条目见[理论清单](REQUIREMENTS.md)。技术选型属于开发建议，不要求用户具备IT知识。

## 目标和工作顺序

CRA打开系统后应接着上一次工作做，直接看到适用于当前项目、中心、受试者和阶段的要求。

1. 访前读取上次遗留，按模板选几项形成访视信草稿。
2. 到中心先看完整遗留问题，核实改了什么、是否改对。每项显示原问题、位置、建议及具体出处、修改现状、复核结果和下一步。
3. 按已描述的常规顺序，整改复核完成后进入新的监查；打开一名受试者，按阶段查看需要完成的检查，同步看源资料与EDC。
4. 检验报告可与EDC检验导出比较一致性和逻辑。出现异常时展开项目具体要求、完整条件及原文，支持CRA形成基本判断和针对性问题。
5. 记录正常核查范围、异常和待办，生成监查报告、访后材料及Excel track。
6. 下次保留同一问题编号及全部过程，继续核实未完事项。

现场仍有个别遗留时怎样安排新的监查，用户尚未细化；不把常规顺序扩大为阻止所有工作的审批锁。必要的紧急安全事项仍需及时处理。

## 规则与资料

共性—项目—中心三层同时生效，适用性和具体条款决定怎样核查。方案、IB、SOP、Q&A、监查计划、手册、项目邮件及文字、中心资料与模板均可提供要求。用户按规则用途提交的明确邮件或文字，无冲突时直接纳入，不因媒介再确认一遍。

全部list采用：关键要求→完整条件与例外→具体事项子清单→原文依据。系统先提取，用户确认、增删和修正。条款、版本、数字、单位、条件、例外、脚注和格式含义要保留。冲突、缺项、无法识别直接告知，不能编造。

## 核查与判断

患者事实尽量从EDC或源记录获取，正常范围简记，异常详细记。系统提供基本分析、合理解释和有依据的追问；最终医学判断由适当人员完成。分级、严重性、相关性、预期性、DLT等分别处理，不相互推断。

自动图片识别与逐字段比对仅限检验报告；其他资料保留人工引导和记录。无法识别可补录或跳过，跳过保留未核实范围。复杂识别能力可在首个可用工作流后接入。

## 问题、报告及四阶段

PD需要报告时附项目依据提醒并跨次跟进；用户说已上报即完成该上报任务，不能自动关闭其他整改。正式EDC Query与系统问题草稿分开，超期必须有实际时间和项目时限来源。ISF/TMF按目录提醒缺件。

启动、访视、关闭、交接共用记录、使用各自清单。关闭依据项目资料和项目组讨论；交接只需说清无遗留，或遗留的前因后果及继续工作。

报告、访视信和track共用事实。已签发报告保存快照，新进展进入后续材料。生成文件不等于已发送、已上报、已签发或问题已完成。

## 尚缺资料不妨碍开发的处理

IB/安全参考资料、填写说明、Q&A、实际SOP、ISF/TMF目录和输出模板尚未齐备时，开发使用合成样例；功能应允许替换为获授权的真实配置。不能把合成示例写成项目已批准规则。真实方案曾发现的表述差异继续列为待澄清，不在公开仓库复制其原文或替项目组裁决。

## 后续更新

本基线是进入开发的起点，后续通过固定编号及变更记录增量完善。原Notion讨论页保留来源；不要求为每一次普通规则内容变更重写全部架构。详见[同步规则](../traceability/SYNC_POLICY.md)。
