# 新闻日报 — V2.1 唯一实施规范与验收清单

**生效版本：2026-10-14，经用户本轮明确纠正。此文仅适用于新闻日报；内参系统是另一个独立系统。**

> **时间、配置的机器权威仅为 [production_policy.json](production_policy.json)，由 Python 读取、由 CI 核验 GitHub Actions cron；本文为人的理解和验收标准。**
> 此前任何 07:00 发送、06:00 截稿、01:00 截稿等旧描述与本文件冲突时，一律按照此处的“凌晨 01:00 发送 + 零点截稿”执行。旧说明保存于 HISTORY_BEFORE_20261014.md，不得用于生产。

## 一、唯一生效的时间合同

| 项目 | 北京时间 | UTC 时刻及 GitHub Actions |
|---|---|---|
| 截稿 | 每日 00:00 | 前一日 16:00 UTC |
| 预先制作 | 00:05、00:20 | 前一日 16:05、16:20 UTC |
| 正式发送目标 | **凌晨 01:00**，首次触发 01:03 | 前一日 17:03 UTC |
| 补偿检查 | 01:16、01:29、01:42、01:55 | 前一日 17:16、17:29、17:42、17:55 UTC |
| 过期禁止 | 02:00（不含）以后禁止交接 SMTP | 前一日 18:00 UTC |

- 版期定义：北京时间当日 00:00 截止的前 24 小时，前一日 00:00（含）至当日 00:00（不含）。
- 提前完成的邮件通过 `manifest.json`（版期、截稿、主题、SHA-256 哈希）和 PDF、HTML、TXT 打包，跨 GitHub Actions 运行恢复。
- 凌晨 01:00 之前不准实际 SMTP 发送；01:00 后发送阶段先恢复当日报告，尽量不重新抓取。提前制作错过后允许补偿制作，但到 02:00 仍未完成则必须失败/告警。
- 正式发送时刻与内容截稿不同是有意的：为了满足提前制作和可靠发送，需要保留制作时段。若想把 01:00 以后发生的新闻包含进 01:00 的成品，会与提前制作形成逻辑冲突。
- GitHub Actions `schedule` 为尽力调度，仓库 24 小时可访问不意味着平台保证分钟级执行。必须核对 schedule 运行是否真的被创建。

## 二、编辑产品合同

- **内容长度**：重要复杂新闻深度报道，普通新闻适度精简；关键事实、数字、人物、时间、背景、争议与后续节点不可丢失，禁止机械摘要化。
- **重大新闻分析**：事实与推论清晰区隔；当日核心变化、因果链、影响路径、反例与可验证变量。
- **整期观察**：末尾《今日关键变化》，围绕 1–3 条关键结构性变化论证，不逐条复述新闻标题。
- **头版**：美股与全球资本市场，包括核心指数快照及日期、Fed/SEC/官方经济统计、重大业绩和机构分析；不能把实时指数仪表盘当成新闻正文。
- **全球覆盖**：中国与美国栏目常态合计 3 篇，国际政治、AI 与科技、产业、创业商业、医疗生命科学等保留，重大事件不受配额阻碍。
- **新闻价值**：必须是真实、重要、有社会/政治/经济/科技影响的新事实或进展；同事件多来源合并但不可误删后续重大进展，反娱乐八卦与宣传软文。
- **来源/版权**：每条可追踪到真实原始来源；机器翻译不改变语气、数字、时间。第三方版权正文不得默认全文转载。
- **预算**：目前已部署 `EditionBudget` 保留更严格 **人民币 1.00 元/期上限**；用户批准的最高容许是 1 美元/期，但在实际汇率换算及账单证据完成前，不扩大生产授权。

## 三、系统职责与失败定义

```text
RSS及官方原件 -> 事件/选题 -> 来源忠实报道/翻译/分析
    -> PDF+Email + manifest（准备完成 PREPARED_NOT_SENT）
    -> 01:03 起只发送核验通过的当日报告
    -> SMTP_ACCEPTED + 当日 receipt / ALREADY_SENT / FAILED
```

- `PREPARED_NOT_SENT`：只证明有准备缓存，不证明发信。
- `SMTP_ACCEPTED`：SMTP 接受，但不等于收件箱已送达。
- `ALREADY_SENT`：当日 SMTP receipt 缓存已存在，未重复发送。
- `SMTP_ACCEPTED_RECEIPT_UNVERIFIED`：SMTP 已接受，但去重凭据未确认，禁止自动盲目重试。
- `FAILED`：未能确认 SMTP 交接，必须有日志及异常状态。
- GitHub Actions cache 是**尽力去重**，非数据库事务锁；极端并发和在 SMTP 接受后任务中断仍可能产生重复或不确定状态。暂未实现严格 exactly-once。
- 七日外部巡检可协助发现漏发，但是目前没有 GitHub Actions 之外的独立自动补发执行器。

## 五、定时故障的证据与边界

- `2026-10-13T03:22:55Z` 的 [schedule run](https://github.com/pyzz58/gpt-recommendations/actions/runs/38341435043) 在北京时间 11:22 创建，且从旧版工作流读取到已存在的发送 receipt，邮件发送步骤被跳过。该绿色 run **不能被报告为发送成功**。
- `2026-10-14` 的已知 [补发运行](https://github.com/pyzz58/gpt-recommendations/actions/runs/38450465689) 由 `push` 触发，不能证明 `schedule` 正常。
- GitHub 官方承认排队拥堵会使 `schedule` 延迟乃至丢弃；但每一天漏发究竟为何原因，需要比对实际触发列表及日志，不可未经证据直接推定。
- 生产流水线的定时可靠性最终以真实 schedule 事件和用户收到邮件验证，而不是 PR 测试绿灯。

## 六、更新治理

1. 后续产品要求先更新 `production_policy.json`（若涉及时间、版期、预算等机器可读项），同时更新本文件中对应的人类合同。
2. 代码和 Cron 只能读取或通过测试严格对齐上述合同。不能仅修改 README 或旧文档来改变运行。
3. PR 必须完整通过单元测试、时间表核验、新闻来源与 PDF 集成检查。
4. 未经验证不得宣布发送、可靠性或内容质量已验收；内参系统不在此次变更范围内。
