# 医疗一人项目｜目录协作规则

适用范围：`pyzz58/gpt-recommendations` 仓库内的 `医疗一人项目/` 目录及其后代。不要据此修改同仓库其他项目的规则或内容。

## 当前阶段

用户明确要求先讨论理论，记录目的、设想、需求和构思。本目录当前保存理论源头，不启动代码实现、部署、模型训练、付费调用、对外联络或真实实验。

后续用户明确授权某项实施工作时，按新的范围执行，不对同一项已获授权工作反复询问；同时维护理论与实现的追溯关系。

## 每次工作先读

1. `CORE_THEORY.md`：核心目的与理论。
2. `DECISIONS_AND_QUESTIONS.md`：明确方向、建议和未决问题。
3. `DISCUSSION_LOG.md`：涉及的历史修正。
4. `SOURCES.md`：引用外部依据时核对其范围。

用户最新明确指令优先。不能把助手先前建议、未验收代码或模板当作用户已确认决定。

## 必须保留的方向

- 初始路线为已有药物用于宠物；未经用户修改不转向其他项目。
- 先验证工作模式，再按实际证据决定是否深入研发或扩大投入。
- 完整覆盖科学判断、研发运营和外部执行统筹，不固定限制三个岗位。
- 低成本通过任务范围、项目数、按需调用和阶段控制实现，不删除关键职责后仍宣称流程完整。
- AI首席科学家是待验证的工作角色，不虚构真实履历、资格、科研成果或专家背书。

## 讨论和记录

- 区分用户决定、助手建议、可核事实、推断和待验证假说。
- 每项新需求注明目的及影响；先更新主文件，再同步相关记录。
- 不抹除历史纠正，不把新技术方便性变成改变目标的理由。
- 遇到角色重叠、证据冲突或工作缺口，记录具体问题及备选方案，不自行宣称已解决。
- 不把新闻启示、一次已知案例回放、多个Agent一致意见或演示界面视为模式成熟。

## 资料和公开范围

本目录位于公开仓库，初始只保存项目理论和相关公开来源。不要加入密码、令牌、个人医疗记录、他人未公开资料、原始敏感数据或与项目无关的个人信息。

对外发送、采购、实验委托及其他现实操作，依据用户明确授权的对象与范围执行。当前本轮没有这些授权。

## 实施前的条件

先把职责、输入输出、权限、汇报、审核和异常处理讨论到可执行程度，再确定复用或自建技术。未获实施指令，不用继续编写代码代替理论讨论。

本文件用于约束仓库协作；未来科学岗位的具体配置应从核心理论派生，并单独验证能力和运行权限。
