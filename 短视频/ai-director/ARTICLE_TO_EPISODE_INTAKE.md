# 从完整文章到短视频导演团队：第一阶段——可追溯的分集与分镜草案

**实现状态：2026-10-11，纯 GitHub 代码研发与合成自动化测试。** 新增 `article_intake.py`，并沿用 `director.py` 的 v0.1 方案结构、`agent_team.py` 的十阶段任务账本与 `agent_role_contracts.py` 的专业岗位 Prompt 合同。

这不是完整的 AI 自动导演，也不是可以直接投递视频生成模型的最终制作包。**当前只解决“长文章进系统、拆分主题、挑选某一集、保留出处、做保守候选分镜、启动专业团队第一张任务单”**。后续真正的演员动作、摄影美术、逐镜视频生成提示词、独立 QA 与总导演终审，都需要实际专业 Agent 生成并验证内容；当前项目禁止无独立授权的模型联网和私人文案发送。

## 用户体验目标

用户只上传一次文章。系统先提出“哪些段落适合变成独立选题”的清单。用户指定要做某集（暂默认第一集），随后总导演以这一集的原文及候选草案为依据，组织剧本编辑、动作表演、摄影美术、声音、剪辑动画、AI 视频技术和 QA；最终目标是为选定视频模型输出镜头级可执行制作包。

**本次实现的是流程的前半截，绝不伪装专业角色已经完成创作。**

## 为什么不直接用用户文章作为 GitHub 示例？

`pyzz58/gpt-recommendations` 为公开仓库。用户提供的《上学以后的孩子》只能在明确允许的**私有工作环境**进行后续实际测试，不能把原文、引用数据、个人制作方案、全文 Prompt 或私人账本上传到 Github。当前单元测试使用专门合成的“下雨关窗、图书馆归还书籍”等故事；另生成了 **18 个虚构编号主题** 证明长篇分集识别功能，而不是把用户稿件复制进仓库。

## 模块函数

| 函数 | 能够完成的工作 | 不能完成的事 |
| --- | --- | --- |
| `split_article(source)` | 按 Markdown 数字主题（如 `### 1.` 至 `### 18.`）拆分；支持普通 Markdown 和无标题短文；记录每段精确字符位置 | 不能保证“每个主题就是最优视频集数”，复杂混合小节需要编辑复核 |
| `episode_catalog(source)` | 返回集数候选、标题、原文位置、主题内容长度、医学/法律/金融风险候选及内容摘要字段存在情况 | 不能把标题和 metadata 当公开数据；不评估故事吸引力或新旧话题重要性 |
| `prepare_episode(source, episode_id)` | 从该主题的“说人话”摘取**逐字原文候选旁白**，根据标点拆成 3–8 秒的暂定镜头；计入无声字幕与数据信息待核验；生成符合现有 `director.validate` 的保守候选计划；同步创建 `agent_team.start` 的十阶段任务账本 | 没有创作新旁白、没有审核素材、没有自动摄影剪辑、没有生成可以直接喂视频模型的完整工单 |
| `episode_source_for_team(source, episode_id)` | 只返回当前集的私密原文部分（不是整篇跨主题文章），用于匹配岗位 `source_digest`；完整文章另用 hash 追溯 | 不会写到 GitHub、公开日志或网络服务 |
| `prepare_first_department(source, episode_id)` | 取得该集的 `plan`、十阶段 `team` 和 `director_brief` 总导演第一张任务封套 | 不会运行 DeepSeek、不生成导演台词或终审、也不自动付款 |

安全约束：
1. 原始文章和提取后的计划只以调用者拥有的 Python 对象存在于内存。**返回对象里可能含有私人文章原文引句和分集标题，所以不能直接把返回值写入公开仓库/日志**。`team` 账本本身只记录哈希、任务与修订号，仍应视为项目私有数据。
2. `source_sha256` 对应完整文章；`episode_source_sha256` 与 `team.source_digest` 对应当前这一集的原始章节（从头到尾，包括来源/备注）。前者保证来源版本，后者避免拿整篇 18 个主题同时给每个专业 Agent 导致串题和高成本。
3. `shot_source_spans` 精确追溯每个候选旁白对应原稿的字符起止位置。只要不能逐字匹配，立即报错，不擅自改写或合并数字。
4. 文章可能不足、没有“说人话”、太长导致时长超限。系统公开标注 `needs_script_editor`、`omissions` 以及 `NARRATION_ABRIDGED_WITH_EXPLICIT_OMISSIONS`，而不是假装已经得到一个可以直接发布的 60 秒成片。
5. 所有 `claims.status` 为 `needs_review`，图片角色、背景、拍法、配音、表演及授权都不是已审核完成的成果。将数据标作待核验，**不会因为引用了来源 URL 就自动标记 verified**。
6. 目前一律只为每条候选引用生成后期字幕/数据信息占位图：`text_card` 与 `data_graphic`，没有伪装成专业 AI 真人演绎的逐镜提示词。可用 `director.validate` 核查结构，但 `director.compile_prompts` 不会因为占位图而捏造生成模型 prompts。
7. 所有审阅标志均 `False`：`narration_approved`、`omissions_approved`、`data_claims_verified`、`visual_directing_complete`、`ready_for_video_model`、`paid_model_authorized`。总导演第一张任务单的“待执行”不等于已经调用 AI 或拿到成片。

## 本期产出与完成判据

本次离线自动测试包含：18 个虚构栏目归档、章节重复号/缺号、代码围栏标题误报、没有结构的普通短文、无候选旁白阻断、超长旁白明确省略、数据未验证、来源逐字定位、正式 `director.validate`、十阶段 `agent_team` 首包及 `agent_role_contracts` 私有 Prompt 构造、整篇文章篡改拦截、无模型/视频调用和零付款。

这一阶段的验收是：**文章可以进入已有导演团队，并交给正确岗位做下一步工作**。下一阶段优先级是剧本编辑/总导演对候选旁白、集数和时长进行正式选题及删改提案，再到多专业实际 AI 创作。真正的端到端验收必须用用户批准的测试文案，在获许可的私人执行位置试运行，并检查镜头可拍性、视觉一致性和后期制作清单是否达到可以直接交给视频生成模型的程度。

不要求用户现在安装依赖、运行 Mac、本地同步、输入 API Key 或付费。
